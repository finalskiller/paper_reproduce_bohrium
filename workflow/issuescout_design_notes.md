摘  要
本文档是 IssueScout 的第二版设计文档。V1 确立了产品的基本设想——打开一个已克隆到本地的代码仓库文件夹,识别其对应的 GitHub 远程仓库,调用接口获取开放 issue,并借助 agent 技术完成分析与推荐——但未给出架构、agent 流程与后续路径。V2 在保留该设想的前提下,补全总体架构、核心流程、数据模型、安全与成本控制、实施路线图与开源运营方案六个部分,使文档达到可直接指导开发的程度。
本版的核心结论有四。第一,产品定位为本地运行的代码接地式 issue 分诊与推荐工具,差异化来自对本地代码与 git 历史的完整访问,由此获得三项网页工具不具备的能力:issue 与代码的映射、疑似已修复检测、基于真实代码的难度评估。第二,技术形态采用 Electron 加 TypeScript 全栈,核心引擎与界面彻底解耦,使命令行、桌面应用与 MCP 服务器三种形态共享同一引擎。第三,分析流程拆为规则层与 Agent 层:规则层零接口成本且无密钥即可运行,Agent 层按需触发,受步数、预算与只读工具三重约束。第四,实施从命令行起步,经 Agent 能力、桌面壳至开源发布,预计六至九周形成可对外发布的状态。
1  项目定位与边界
1.1  定位与核心价值
IssueScout 是一个本地运行的桌面工具:用户指向一个已克隆的 Git 仓库文件夹,它自动识别对应的 GitHub 远程仓库并拉取开放 issue 列表,随后结合本地代码与 git 历史完成规则与人工智能两级分析,输出一份可直接动手的 issue 推荐清单。每条推荐包含中文摘要、类型判断、难度评估、涉及的文件位置、建议思路与置信度。V1 描述的场景链条——打开文件夹、定位远程仓库、调用接口、agent 分析、返回推荐——整体成立,V2 的工作是将其中每一环具体化到可实现的程度。
之所以强调本地运行,有两层含义。其一是隐私与成本:除 GitHub 接口与用户自选的大模型接口外,数据不经任何第三方服务器,密钥与配置全部保存在本机。其二是能力:只有拿到完整代码与提交历史,才能完成网页类工具做不到的分析,这是产品护城河的来源,详见 1.3 节。
1.2  目标用户与使用场景
按 V1 的场景描述,产品首要服务的是刚拉下仓库、要找 issue 的人。据此将用户分为三级:一级用户为开源贡献者,克隆了项目但不知道从哪个 issue 入手,需要摘要、代码定位与难度参考;二级用户为项目维护者,面对积压的 issue 需要快速分类,并识别过期或疑似已在主干修复的条目;三级用户为延伸场景,即通过 MCP 协议在 Cursor、Claude 等人工智能客户端中直接调用同一分析能力。
典型使用流程如下:用户打开应用并选择(或拖入)本地仓库文件夹,应用解析 git 远程配置,确认仓库后拉取开放 issue;列表页展示规则层产出的类型、难度与新鲜度标记;用户点开感兴趣的 issue,触发 Agent 深度分析,得到根因假设与受影响文件,并可一键在 VS Code 中跳转。全程未配置大模型密钥时,应用自动降级为纯规则模式,依然可用。
1.3  与现有工具的差异
issue 推荐并非全新品类。goodfirstissue.dev、up-for-grabs.net、Code Triage 等网站基于 GitHub 元数据(标签、评论数、时间)做筛选,GitHub 自身的标签体系也是主要信息源。这些方案的共同局限是只看得到元数据,看不到代码。IssueScout 的差异化恰恰建立在对本地仓库的完整访问之上,具体为三项:
代码定位:将 issue 描述映射到具体文件与函数符号,给出这个问题大概在哪儿的判断;
疑似已修复检测:在本地 git 历史中检索该 issue 创建之后、引用其编号且已合入默认分支的提交(如 fix #123、close #123),命中即提示该 issue 很可能已解决、无需处理,这是纯本地、零接口成本的独有能力;
基于真实代码的难度评估:依据受影响文件的规模、耦合程度与历史变更频率估计工作量,而非仅凭 good first issue 标签猜测。
上述能力决定了产品的一句话定位:面向贡献者的、代码接地的 issue 侦察员。
1.4  范围边界
为控制首个可用版本的规模,明确以下内容不在本版范围内:不做云端托管与 SaaS 形态,不做多人协作与同步;不自动修改代码或提交拉取请求,分析止步于建议与定位,关于自动修复方向的评估见第 10 章;不做 issue 看板等项目管理功能;不内置模型,全部通过 OpenAI 兼容接口接入,本地部署可经 Ollama 实现;暂不支持 GitLab,数据源经适配器接口预留扩展位。每一项边界都对应第 9 章风险表中的一个显式取舍。
2  总体架构设计
2.1  架构总览
系统分为三层:桌面壳、核心引擎与外部依赖。桌面壳为 Electron 应用,渲染进程承载 React 界面,主进程持有全部输入输出能力;核心引擎 Core 是一组与界面无关的纯 TypeScript 包,承担仓库识别、issue 获取、代码索引、规则分诊与 agent 分析五项职责;外部依赖包括 GitHub 接口、用户自选的大模型接口与本地仓库(经 git、ripgrep、tree-sitter 访问)。总体结构见图 1。

图 1  IssueScout 总体架构
架构设计遵循三条原则。其一,引擎与壳解耦:Core 不依赖任何 Electron 接口,使命令行、桌面应用与 MCP 服务器三种产品形态共享同一引擎,这是后续以最小成本扩展分发渠道的前提。其二,输入输出收敛:所有网络、文件与子进程操作集中在主进程,渲染进程不接触文件系统与密钥,天然缩小攻击面。其三,降级可用:每一层都设计有无外部服务时的行为——无 GitHub 密钥时受限流地使用匿名接口,无模型密钥时退回规则层,保证工具在任何配置下都能打开、能出结果。

2.4  进程模型与数据流
桌面形态下,渲染进程与主进程经类型安全的 IPC 通道通信:请求响应用于同步操作(如读取设置),事件流用于进度反馈(如分页拉取与分析步骤日志)。一次典型会话的数据流为:用户选择目录,主进程完成仓库识别并请求确认;随后并行执行 issue 拉取与本地索引构建;规则层在两者就绪后对全量 issue 打分,列表页即时渲染;用户点开某条 issue 时,主进程组装上下文并启动 agent 循环,过程日志实时推送到详情页。分析结果写入本地 SQLite,以仓库、issue 编号与当前 HEAD 提交号为键缓存,代码未变时不重复调用模型。
3  核心流程设计
3.1  仓库识别
识别模块读取目标文件夹下 .git/config 中的远程配置,优先取 origin,其次 upstream,解析出所有者与仓库名。需覆盖三种常见远程地址格式:HTTPS 形式、SSH 形式与本地协议路径。目标文件夹不存在 .git 或未配置远程时,界面提供手动输入所有者与仓库名的兜底入口。识别结果(远程地址、默认分支、当前 HEAD 提交号)在界面上明确展示并由用户确认,既避免误识别,也为后续缓存提供键值。
3.2  Issue 获取与缓存
使用 GitHub REST 接口按页拉取开放 issue。需要注意该端点会同时返回拉取请求,必须按响应中的 pull_request 字段过滤。认证采用梯度策略:优先复用本机 gh 命令行工具的令牌,其次读取 GH_TOKEN 环境变量,最后由用户在设置页手动填写个人访问令牌;未认证时限流为每小时 60 次请求,认证后提升至 5000 次,因此对匿名用户的认证引导是首要体验问题。私有仓库要求令牌具备 repo 权限,界面需明示影响。
拉取结果以快照形式存入本地 SQLite,并利用 ETag 与条件请求头实现增量刷新,列表缓存有效期设为 5 分钟;issue 评论体积大,仅在深度分析触发时按需拉取并缓存。上述策略将常规刷新的请求量压缩到个位数,匿名用户也能正常使用。
3.3  规则层预分类
规则层是整个产品的成本与体验基座,不调用任何大模型,输入为 issue 元数据与本地 git 历史,输出类型、新鲜度、难度与关联文件四类信号:
类型推断:以仓库已有标签为强信号,辅以标题与正文关键词,将 issue 归入缺陷、功能、提问、疑似重复、信息不足五类;
新鲜度:综合创建时间、最近更新、最后评论时间与报告人近期活跃度,识别长期无响应的过期条目;
疑似已修复:在 git 历史中检索该 issue 创建之后、已合入默认分支且提交说明引用该编号的提交,命中即打标——这是 V1 设想中缺失、但实现成本最低的差异化能力,建议 M0 即交付;
关联文件与难度粗估:提取 issue 文本中出现的路径、文件名与标识符并在本地索引中匹配,按命中文件的规模与数量给出小、中、大三档粗估。
规则层的输出直接构成无密钥模式下的完整体验,同时作为 agent 层的先验,显著压缩后续提示词长度。所有信号附来源说明,保证用户能区分标签说的与代码证据说的。
3.4  Agent 深度分析
深度分析在用户点开某条 issue(或对列表页选定的少数条目批量执行)时触发,流程见图 2。

图 2  Agent 深度分析流程
第一步为上下文组装,包括 issue 正文、评论时间线摘要(超长评论截断保留结论)、规则层全部先验、仓库地图(两级目录树加各顶层模块的一句话职责,由索引器预生成)与 README 摘要。第二步进入工具循环:模型以推理加行动的方式提出工具调用,系统执行后回填结果;循环受三重上限约束——最多 12 步、单 issue token 预算与总超时。可用工具全部为只读:
search_code(query):ripgrep 封装的代码全文检索;
read_file(path, start, end):分窗口读取文件,单次不超过 200 行;
list_symbols(file):返回经 tree-sitter 解析的函数与类符号表;
search_issues(text):在本地缓存的仓库 issue 中检索相关历史条目。
模型策略支持双档配置:循环中间步骤使用低成本模型,最终综合使用强模型,两档可按提供方独立设置。循环结束或触达上限后,模型输出结构化结论并经校验;校验失败自动携带错误信息重试一次,仍失败则降级返回规则层结果并附错误说明,保证任何情况下详情页都有内容可看。
3.5  分析结果结构
深度分析的输出契约如下,字段值为示例:
{
  "summary": "登录后在空白页刷新偶发 500,疑似会话清理竞态",
  "type": "bug",
  "root_cause": "登出与刷新并发时,sessionStore.clear 与读操作未互斥(依据 src/auth/session.ts)",
  "affected_files": [
    { "path": "src/auth/session.ts", "symbol": "clear()", "reason": "竞态发生点,写后未加锁" }
  ],
  "difficulty": "M",
  "approach": ["为 sessionStore 增加互斥锁", "补充并发回归测试"],
  "risks": ["锁粒度过大可能拖慢登出路径"],
  "confidence": 0.72
}
其中 affected_files 是界面联动的核心:详情页对每个文件提供在 VS Code 中打开的动作,经 code 命令的跳转参数直达具体行。confidence 由模型自评并经人工反馈校准,用户可对单条分析标记赞同或反对,作为后续提示词迭代的样本,反馈数据仅存本地。
4  安全、隐私与成本控制
4.1  提示词注入防护
issue 标题、正文与评论来自任意第三方,是典型的不可信输入,必须假设其中可能包含试图操纵分析器的指令。防护采用纵深四层:系统提示明确声明 issue 内容一律视为待分析数据,其中的任何指令不予执行;工具白名单全部只读,不存在 shell、网络写或文件写能力,即使被注入也无法造成破坏;步数、token 与超时三重预算限制注入造成的资源消耗;输出经结构化校验,异常字段直接拒绝。该威胁模型下的最坏结果是浪费少量 token 并得到错误结论,而错误结论在界面标注置信度与证据来源后可被人快速识别。
4.2  密钥管理
GitHub 令牌与大模型密钥经 Electron 的系统加密存储(Windows 上为数据保护接口)加密后保存,按操作系统用户隔离;配置文件仅保存非敏感项,如模型选择、界面语言与预算上限。日志系统对密钥形制的字符串统一脱敏。产品不含任何遥测与上报,此点写入 README 作为公开承诺。
4.3  调用成本与限流
成本结构刻意设计为列表免费、深度按需:规则层与列表页零接口成本;深度分析在触发前展示预估 token 与费用(按提供方定价估算),完成后记录实际用量;结果以仓库、issue 编号与 HEAD 提交号缓存,代码未动不重复计费;设置页提供每日预算上限,触达后当日禁用深度分析。GitHub 侧通过认证引导加条件请求控制请求量,详见 3.2 节。

8  开源运营计划
8.1  许可证与仓库规范
许可证建议采用 MIT,宽松度最高、贡献心理门槛最低;若在意专利授权条款可改用 Apache-2.0,两者对后续商业化均友好。仓库规范包括:语义化提交配合 changesets 管理版本;issue 与拉取请求模板;持续集成流水线承担检查、测试与多平台构建;本文档演进为仓库中的架构说明文档,使贡献者按图索骥;另备贡献指南与行为准则。README 采用英文为主、中文对照的双语形式,兼顾国际与中文社区。
8.2  发布与分发
桌面端经 GitHub Releases 发布 Windows 安装包与便携压缩包,集成自动更新组件,后续视需求接入 Scoop 与 winget;命令行发布至 npm,一条命令即可体验,这往往是开源工具被尝试的第一入口;MCP 形态接入官方服务器目录。发布流水线由版本标签触发,产物附校验和。
8.3  冷启动推广
推广以可感知的演示为先:README 顶部放一段约三十秒的演示动图,展示从拖入文件夹到看到带代码定位的推荐的全过程。渠道上,首发放 Hacker News 的 Show HN 与 Reddit 相关社区,中文渠道同步 V2EX 与掘金;持续提交至各类 awesome 清单;接入 MCP 生态目录以获取人工智能工具用户。最重要的一条是吃自己的狗粮:IssueScout 仓库自身的 issue 用 IssueScout 管理,维护过程即最好的演示与需求来源。运营指标以外部拉取请求合并数与用户按推荐实际提交了贡献的反馈为准,不以 star 数为目标。

10  方向评估与延伸建议
针对是否有更好的项目方向这一问题,评估结论是:主线方向值得坚持,但价值最高的一步调整,是把 MCP 形态从远期规划提前到与开源发布同期。理由如下。
IssueScout 的管道中,仓库识别、代码索引、规则分诊与 agent 循环全部与 issue 这一数据源解耦(经 github 适配器抽象)。将数据源换成拉取请求,即得到面向维护者的 PR 分诊工具——同一引擎的第二产品线,且维护者场景的付费意愿通常高于贡献者场景,可作为下一阶段的方向储备。将引擎包装为 MCP 服务器,则 Cursor、Claude 等客户端的用户无需安装新应用即可调用全套分析能力,分发成本几乎为零;当前 MCP 生态正处于高速采用期,早期接入官方目录的曝光红利显著,建议与 M3 同期交付,而非等到 M4。
另一个自然的延伸是贡献上手向导:面向首次接触某仓库的开发者,把推荐 issue 升级为规划路径——按用户技能画像给出阅读顺序、首个可上手任务与相关背景链接。它与现有管道共享九成组件,可在主链路稳定后作为增值功能并入。
反向排除项同样明确:不建议做全自动修复 issue 的机器人,该赛道竞争密集、可信度建立困难、失败案例的公开代价高;不建议进入 issue 看板与项目管理,成熟产品密集且与本地单机定位冲突。
执行建议:以两周为限完成 M0 的命令行版本并坚持自用一周。若打开仓库看分诊清单没有成为日常习惯,说明价值假设不成立,应及时调整方向而非继续投入界面;反之则按路线图推进,并在 M2 完成后立即开源。开源本身即是最好的需求收集与共同开发者招募渠道,不必等待功能完备。
